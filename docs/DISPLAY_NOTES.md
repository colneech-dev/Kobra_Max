# Kobra Max display — everything we know

Working notes for the **KobraMax-HC32** touch display (DWIN T5L1, "DGUS II"), written 2026-10-25 so the
knowledge from a long debugging effort is not lost. Read this before touching anything under
`DWIN_SET/`, `tools/`, or `source/Marlin/src/lcd/extui/lib/anycubic_dgus/`.

* **Part 1** — what the display is and how it works (facts).
* **Part 2** — file and record formats (reference).
* **Part 3** — how to do things (recipes: new screen, animation, progress bar, pressed button, flashing).
* **Part 4** — what works, what is unproven, what failed.
* **Part 5** — the tools in `tools/` and how they fit together.
* **Part 6** — pitfalls we hit (read this list once, it will save days).

Status legend used throughout: **[HW]** = confirmed on the real printer, **[SPEC]** = from DWIN's
documentation but not yet seen on our hardware, **[RE]** = reverse-engineered from files, **[?]** = unknown.

# Part 1 — How the display works

## 1.1 The hardware

| | |
|---|---|
| Display module | DWIN **T5L1**, firmware banner on the blue download screen: `T5L1 DGUS2 V4.7 2022.02.24` **[HW]** |
| Resolution | **272 × 480**, portrait, 24-bit colour |
| Link to the mainboard | UART, **115200 8N1**, to the HC32F460's **USART4** (TX = PB10, RX = PH2). Pins must have the sub-function bit (BFE) **cleared**. **[HW]** |
| Flash | 16 MB, divided into **64 fixed 256 KB slots** (see 1.4) |
| Brains | The display runs its own program ("DGUS"); the printer firmware never draws anything. It only (a) writes values/text into the display's variable RAM and (b) reads key presses. |

The model to keep in your head: **the display is a dumb-but-smart terminal.** The mainboard sends
"put this text at variable 0x2060" or "go to page 8"; the display decides how and where it is drawn,
using layout data that was flashed into it beforehand.

## 1.2 The four things that must agree

A screen is not one thing. It is four independently flashed things that have to line up exactly:

```
 PICTURE LIBRARY         SHOW FILE (14)           TOUCH FILE (13)         FIRMWARE (dgus_tft.cpp)
 16_68_.icl              14ShowFile.bin           13TouchFile.bin         page handlers
 -------------------     -------------------      -------------------     -------------------
 the background image    "draw variable 0x2030    "a tap inside (8,429)-  "page 8, key 5 =
 of every page, built     here, in this font,      (132,473) on page 8      home X axis"
 from BMP files           this colour"             returns key 5"
 (DGUS IDE, manual)      (generated by script)    (generated by script)   (C++)
```

If any one disagrees with the others you get the classic symptoms: text drawn in the wrong place,
buttons that do nothing, buttons that act on the wrong thing, or a page that looks right but ignores
touch. `tools/cross_check_display.py` checks the first three against each other and against the C++.

## 1.3 Pages, language mirrors, and numbering

* A **page** is a number. Page *N* = background picture *N* in the picture library + the records for
  page *N* in the show file + the touch zones for page *N* in the touch file.
* Page IDs start at **0** (the boot page). **The page table in `14ShowFile.bin` is indexed by page ID
  starting at 0** (entry for page N is at byte `16 + 4*N`). We generated it 1-based for months, which put
  every page's records on the page *before* it. Proven against the stock file (file list = page 2 =
  table index 2). **[HW]**
* The stock firmware has a Chinese set (pages 1–34) and an English mirror at **+120** (121–154). Our art
  is English in both, so the mirrors are identical. The firmware's default language is ENG
  (`anycubic_dgus_lcd.cpp`), so the ENG pages are the ones normally shown.
  `DgusTFT::TranslatePage()` maps a "CHS-domain" page number to the real one for the current language.
* **Device page vs CHS-domain page — the classic bug.** `page_index_now` / `page_index_last` hold the
  *already translated* (device) page. To go back to one, call `ChangePageOfTFT_DevicePage()`. Calling
  `ChangePageOfTFT()` with a stored page translates it a second time (ENG 131 → 251, a page that does
  not exist) and freezes the display. Never subtract/add 120 by hand.
* **Never send a page change while the boot animation is playing** — the display freezes. Wait for
  `REG_LCD_READY` (VP `0x0014`) to report `0x010072`; the display pushes it by itself when the
  animation finishes. **[HW]**

## 1.4 Flash slots — the rule that bit us

The 16 MB flash is 64 slots of 256 KB. **A file is written to the slot given by the number at the start
of its file name and occupies as many consecutive slots as its size needs** (`ceil(size / 256 KB)`).
Picture space is slots 16–63; fonts/icons/configs share the 4–12 MB region (guide section 2.5).

| File on the SD card | Slot(s) | What it is |
|---|---|---|
| `0_DWIN_ASC.HZK` | 0–11 | Built-in ASCII fonts (4×8 up to 64×128 dots) |
| `16_68_.icl` | 16–24 (max 9 slots, 2,359,296 bytes) | Background picture library (all pages + pressed pictures) |
| `25_ICO.icl` | 25 | Stock Anycubic icon library (popup dialogs, toggles, bulbs). *Was `23_ICO.icl`.* |
| `26_FontSong14X14.DZK` | 26–28 | Chinese 14×14 font. *Was `24_...`.* |
| `29_SPIN.icl` | 29 | Spinner icon library (optional; you build it) |
| `34_BootAnim.icl` | 34 | Boot-animation frames (parked, not shipped) |
| `13TouchFile.bin`, `14ShowFile.bin`, `22_Config.bin`, `T5LCFG.CFG`, `DWINOS.bin` | (configuration area) | touch zones, display records, initial values, hardware config, OS |

**Why `23_ICO.icl` and `24_Font…` were renamed:** the stock picture library is 7 slots (16–22) so the
icon library fits at 23. Our rebuilt library is bigger (9 slots) and runs through 23 and 24, silently
overwriting the icon library and the start of the font. `tools/ui_features.py → FLASH_RENAMES`
moves them, and `tools/check_icl.py` reports any overlap. The CFG file (`T5LCFG.CFG`, byte 0x08) pins
only the *background library's* slot (0x10 = 16); nothing pins the icon library or font.

Limits from the guide: a single picture inside a library must be **≤ 248 KB** on T5L1; a single icon
library file that exceeds 256 KB must be counted slot-by-slot; icons are ≤ 1024×1024.

## 1.5 Variables ("VP"s) — how the firmware talks to the screen

Everything dynamic is a **16-bit word address** in the display's variable RAM ("VP"). A *display
control* in the show file watches one VP and draws it; a *touch control* writes a key code to one.

* Text VPs hold a string terminated by `0xFFFF`. Each text VP in our layout owns a **0x30-word window**
  (so VPs are spaced `0x30` apart). A string longer than the control's `Text_Length` is cut off.
* Number VPs hold a 16-bit integer.
* `0x1000` (`KEY_ADDRESS`) receives the key code of whatever was tapped; the display also *pushes* the
  value to the mainboard as a read-reply frame, and the firmware dispatches on `(page, key)`.
* The full VP list is in `dgus_tft.h` (`TXT_*`, `ADDRESS_*`) and is mirrored in `tools/patch_14showfile.py`.
  `cross_check_display.py` fails if the two disagree.

| VP | Name | Used for |
|---|---|---|
| `0x2030` / `0x2880` | `TXT_MAIN_HOTEND` / `TXT_MAIN_BED` | status bar temperatures (on every page) |
| `0x2090 … 0x2150` | `TXT_FILE_0…4` | file-browser rows |
| `0x2180 … 0x2240` | `TXT_PRINT_NAME/SPEED/TIME/PROGRESS/COMMENT` | Printing / Paused text |
| `0x22A0 / 0x22D0 / 0x2300` | `TXT_ADJUST_HOTEND/BED/SPEED` | Print Settings values (integers) |
| `0x2330 … 0x23C0`, `0x23F0 … 0x2480` | temperature / speed page values | Temperature, Speed & fan |
| `0x2600` | `TXT_LEVEL_OFFSET` | Z offset text |
| `0x2690 …` | About / statistics text | (About and Statistics share addresses) |
| `0x2920 … 0x29E0` | `TXT_TERM_L0…4` | Terminal log |
| `0x2A80` | `TXT_WAIT_STATUS` | live status line on wait screens |
| `0x2AB0` | `TXT_MOVE_STEP` | selected Move-axes step ("1.0 mm") |
| `0x2B00` | `TXT_WAIT_ANIM` | spinner start/stop (1 = run) |
| `0x2B20` / `0x2B30` | `TXT_PRINT_BAR` / `TXT_WAIT_BAR` | progress-bar values (0–100) |
| `0x4300 / 0x4500 / 0x4550` | move step / light state | **stock** icon-VPs; no display record uses them now |

## 1.6 The serial protocol (mainboard ↔ display)

Frames are `5A A5 <len> <cmd> <payload…>` where `len` counts everything after itself.

| Action | Frame |
|---|---|
| Write VP (`0x82`) | `5A A5 <len> 82 <addr hi> <addr lo> <data words…>` |
| Write text | same, data = ASCII bytes then `FF FF` |
| Read VP (`0x83`) | request `5A A5 04 83 <addr> <word count>`; reply `5A A5 <len> 83 <addr> <count> <data>` |
| Key press (display → mainboard) | `5A A5 06 83 10 00 01 <key hi> <key lo>` (VP `0x1000`) |
| **Change page** | `5A A5 07 82 00 84 5A 01 <page hi> <page lo>` (system VP `0x0084`; `5A01` = "switch now") |
| Brightness | `5A A5 07 82 00 82 <active%> <standby%> <time hi> <time lo>` (VP `0x0082`) |
| Sound on/off | writes to VP `0x0080` (`5A 00 00 1A` on / `… 12` off) |
| Start/stop an animation icon | ordinary VP write of its V_Start / V_Stop value |

The parser (`DgusTFT::ReadTFTCommand`) is non-blocking and re-synchronises on `5A A5`.

# Part 2 — File and record formats

All multi-byte values are **big-endian** unless noted. Colours in records are **RGB565**
(`((r>>3)<<11) | ((g>>2)<<5) | (b>>3)`; e.g. our orange (255,107,53) = `0xFB46`).

## 2.1 `14ShowFile.bin` — display controls ("what to draw")

```
bytes 0..7   header (stock; untouched)
bytes 8..9   page count  (we set 218: page IDs 0..217)
bytes 16..   page table, 4 bytes per page ID starting at ID 0:
               u16 LITTLE-endian  number of 32-byte records
               u16 big-endian     absolute file offset of the first record
...          record data (32 bytes each), page by page, from 0x4000 onwards
```

`patch_14showfile.py` never builds this from scratch. It copies **`DWIN_SET/14ShowFile.base.bin`** (the
stock Anycubic file), **appends** new record blocks after the existing data and **rewrites the page
table entries** of every page we use. Pages we do not touch keep their stock records (stock VPs, stock
positions) — so every reachable page must be patched, even if only with the status bar.
Offsets are 16-bit, so the whole file must stay below 64 KB (currently ~37 KB).

### Record types (every record is 32 bytes; first word is the type)

All have `type, SP, 0x000D, VP, …`. **SP** is the "description pointer"; we always set it to `0xFFFF`
("parameters come from this record, not from RAM"). Offsets below are from the start of the record.

**`0x5A11` text display** (guide 7.13) **[HW]**
```
00 5A11 | 02 SP=FFFF | 04 000D | 06 VP | 08 x | 0A y | 0C colour | 0E Xs | 10 Ys | 12 Xe | 14 Ye |
16 Text_Length (we use 0x001E = 30 bytes) | 18 Font0_ID (0 = built-in ASCII) | 19 Font1_ID |
1A Font_X dots | 1B Font_Y dots | 1C mode (0x42 as in stock) | 1D..1F spacing / unused
```
Font size: the built-in ASCII font has every glyph 4×8 … 64×128 dots, **width : height = 1 : 2**
(`10 × 20`, `12 × 24`, `16 × 32`…). Our status-bar and most records still use a squat `12 × 12`; the
step text, wait-status line and terminal log use `10 × 20`. The text is drawn from the top-left of the
box and is **not** centred — make the box exactly as tall as the font and put the art box under it.

**`0x5A10` integer display** — reverse-engineered from the stock file **[HW][RE]**
`5A10 FFFF 000D VP x y FFFF 000A 02 <digits> 00…` — only the top-left corner is stored; colour/size
come from stock defaults. Good for plain numbers (temperatures, percentages).

**`0x5A01` animation icon** (guide 7.3) **[HW]** — see 3.4
```
00 5A01 | 02 FFFF | 04 000D | 06 VP | 08 x | 0A y | 0C Reset_ICON_En | 0E V_Stop | 10 V_Start |
12 ICON_Stop | 14 ICON_Start | 16 ICON_End | 18 ICON_Lib (1 B) | 19 Mode (0 = transparent, else opaque) |
1A Layer_Mode | 1B ICON_Gamma | 1C PIC_Gamma | 1D Time (DGUS cycles, 20 ms each) | 1E Display_mode (0 = loop) | 1F Filter_Set
```

**`0x5A23` process bar** (guide 7.23) **[SPEC]**
```
00 5A23 | 02 FFFF | 04 000D | 06 VP | 08 Xs | 0A Ys | 0C Xe | 0E Ye | 10 border | 12 foreground | 14 background |
16 Var_Max | 18 Var_Min | 1A Mode (0 = border + filled background) | 1B Direction (0 = rightwards) |
1C data type (0 = integer) | 1D reserved | 1E VP_RT (0 = don't return the percentage)
```

**`0x5A04` image animation** (guide 7.6) — page-background slideshow; **parked, not working for us**
(Part 4):
`5A04 FFFF 0005 0000 Pic_Begin Pic_End Frame_Time(8 ms) ICL_LIB_ID(0 = background library) …` — the
control must sit on the page; it plays pictures Pic_Begin → Pic_End and then returns to the page.

## 2.2 `13TouchFile.bin` — touch zones ("what a tap does")

32-byte records, terminated by `FF FF`. Generated by `generate_dwin_controls.py`.

```
00 page (u16) | 02 Xs | 04 Ys | 06 Xe | 08 Ye            the rectangle (inclusive pixel coords)
0A Pic_Next  FF00 = no page switch (we never let the display change page by itself)
0C Pic_On    page whose picture shows over the button WHILE IT IS HELD (FF00 = none)   ← press effect
0E TP_Code   FE05  (touch control "return key code")      10 FE
11 VP        0x1000 (KEY_ADDRESS)                          13 mode 00 (store the code in the VP)
14 key code (u16)                                          16 hold time (0.1 s units)   17..1F zero
```
Stock records mostly carried `FF00` in `Pic_On` (no effect). A copy-paste in our generator wrote a stray
`0x0023` into **every** record, i.e. "show picture 35 while pressed" with no picture 35 in our library —
which is why pressed buttons never changed. Stock UI uses *page + 34* for its pressed pictures.

The key codes are the `case` labels in the `pageN_handle()` functions; they are listed per page in
`tools/DWIN_CONTROLS_README.md` (generated from the zone list — never edit it by hand).

## 2.3 `16_68_.icl` / `*_ICO.icl` — picture and icon libraries **[RE]**

Both use the same container ("DGUS_3"), decodable with `tools/check_icl.py` (it can extract every picture).

```
00  "DGUS_3"                      magic
06  u16  CRC-16 of bytes 8..end    table-driven "Modbus" CRC (init 0xFFFF, auchCRCHi/auchCRCLo, high byte
                                  first). Verified on 6 independent files (check_icl.icl_crc).
08  u32  total file size - 8
0C  4 bytes flags / count         e.g. 04 01 00 00 (ours), 04 00 D6 00 (stock, 0xD6 = 214 pictures),
                                  04 00 45 00 (icon lib, 0x45 = 69 icons)
10  table of u32 absolute offsets, one per picture/icon ID, 0 = absent; the table ends where the
    first picture starts (so its length is (first offset - 16) / 4 entries)

each picture/icon block (blocks are contiguous: next offset = offset + 10 + header_len + data_len):
    u16 width | u16 height | u16 header_len (always 626) | u32 data_len
    then: [JPEG header, header_len bytes] [JPEG entropy data, data_len bytes]
```
* **The JPEG header is byte-identical for every picture of the same size** (all 145 in our library):
  JFIF APP0, two DQT tables (quality ~90, ids 0/1), SOF0 (4:2:0), the four *standard* Huffman tables,
  and the quirky SOS. Only the SOF width/height differ between sizes.
* The count at bytes 13-14: for our IDE-built background library it equals the **highest picture ID**
  (256); for the stock icon library it equals the **number of icons** (69).
* Table length = highest ID + 1 entries; the first block starts right after the table.
* The pictures are **baseline JPEG, 4:2:0, standard Huffman tables**, quantisation tables from the IDE.
  The "JPEG header" is everything up to and including the SOS segment (always 626 bytes for this IDE
  output); the entropy data follows. `data_len` and every block offset are **multiples of 4**; the data
  ends with 8–11 zero padding bytes.
* DWIN's JPEGs break the standard in two ways, which is why ordinary decoders reject them: the **SOS
  segment declares length 15** (a standard one is 12 — three extra zero bytes) and there is **no
  end-of-image marker**. `check_icl.py` repairs both before decoding.
* A library's index = picture ID = page number (background library) or icon ID (icon library).
* The default picture shown at power-on is picture **0**.

**How the header CRC was found:** the DGUS IDE package contains DWIN's own multi-language ICL writer as a
.NET assembly, `DGUS/DGUS_V7649/TOOL/multiLanguage/net8.0-windows/Excel2ICL.dll`. Disassembling it with
`tools/re/il_dump.ps1` showed `Utils.CRC16` (table-driven Modbus CRC) and `Utils.ICL.getICL`, which builds each
block as `[w][h][hdr_len][data_len] + JPEG`, inserts padding so the JPEG header ends on a 4-byte boundary
(that is why the SOS segment declares 15 instead of 12), appends 8 zero bytes and pads to 4, writes the
highest ID as the count, then computes the CRC over bytes 8.. and stores it at 6-7. It also warns "need zero
padding" when a picture would straddle a 16 MB flash-address boundary (irrelevant at our sizes). This tool
writes a 4096-byte header/table area; the IDE's own ICL tool (what produced our library) uses a shorter,
exact-size table — the display accepts both. (`Movie2ICL.exe`, which made `34_BootAnim.icl`, uses a different
CRC variant that we did not decode.)

**Writing it ourselves (experimental) [RE]:** `tools/build_icl.py` builds a library from BMPs: it takes the
JPEG header and quantisation tables from an IDE-built template, encodes each picture with Pillow
(4:2:0, standard Huffman tables, the template's quantisation tables — passed in *natural* order, Pillow
does not want zigzag), pads the entropy data like the IDE does, and writes the container. It refuses to
build if Pillow's tables differ from the template's. Self-test: the IDE's own pictures re-encoded come
out 0.98-0.99x the IDE's size and decode back with 0 differing pixels. What is **not** known: the
header CRC — now computed exactly as DWIN's tool does it, and `check_icl.py` verifies it — and, the real question,
**whether the display's hardware decoder accepts it** (test file:
`release_v2/EXPERIMENTAL_SCRIPT_ICL/`). If it does, the manual IDE step disappears.

## 2.4 `T5LCFG.CFG`, `22_Config.bin`, `DWINOS.bin`

Taken unchanged from Anycubic's official V2.8.7 package. `T5LCFG.CFG` (46 bytes) holds hardware
settings; **byte 0x08 = 0x10** tells the display that the background library is in slot 16.
`22_Config.bin` (131,076 bytes) is the initial-value file; the repo keeps it as `22_Config.base.bin`
and the packager ships it under the real name. **Never generate a `22_Config.bin` from a fresh IDE
project** — a "New Project" one stopped the display from booting (Part 4).

# Part 3 — How to do things

## 3.1 Everyday workflow (change something on a screen)

1. Edit the art in `tools/generate_screens.py` (buttons, labels, boxes).
2. Move the matching **touch zones** in `tools/generate_dwin_controls.py` and the **text/number boxes**
   in `tools/patch_14showfile.py` (or, better, use a row/layout table in `tools/ui_features.py` that all
   three read — see the Print Settings rows).
3. If a button is new: add a `case` in the right `pageN_handle()` in `dgus_tft.cpp`.
4. Run **`python tools/cross_check_display.py`** — it tells you where art, zones, records and handlers
   disagree (typically by a few pixels).
5. Rebuild the picture library in the DGUS IDE (3.6) and run **`python tools/check_icl.py`**.
6. `python tools/build_release.py` → flash (3.7).

## 3.2 Add a text or number field

1. Pick a VP (a free `0x30`-aligned address; add `#define TXT_X` to `dgus_tft.h`).
2. In `patch_14showfile.py` add the same constant and a `make_text_record(VP, x, y, w, h, cw=10, ch=20)`
   (text) or `make_integer_record(VP, x, y)` (number) to that page's list. Keep `w × h` equal to the box
   you draw with `vp_area()` in `generate_screens.py` (cross-check enforces ≥ 80 % overlap).
3. Firmware: `SendTxtToTFT("…", TXT_X)` or `SendValueToTFT(n, TXT_X)`.

## 3.3 Add a progress bar **[SPEC]**

`make_process_bar_record(vp, x0, y0, x1, y1, border, fg, bg)` in the page's record list; draw only the
empty track in the art; firmware writes an integer 0–100 to the VP (`SendValueToTFT(pct, TXT_..._BAR)`).
Used for the print progress (`TXT_PRINT_BAR`) and leveling (`TXT_WAIT_BAR`). First use on hardware is
still pending — if the display misbehaves, set `PROGRESS_BARS = False` in `ui_features.py`.

## 3.4 Make an animation — the animation icon (this works) **[HW]**

The display cannot be told to "play" in a page change. An **animation icon** control cycles through
consecutive icons of an *icon library*, and **plays only while its VP equals `V_Start`** (it shows
`ICON_Stop` for any other value). The firmware therefore *starts and stops it by writing the VP*.
DWIN's guide, section 7.3, and our toggle test on 2026-10-25 agree.

Steps:
1. **Make the frames.** One image per frame, all the same size, numbered by icon ID (`100.bmp`,
   `101.bmp`, …). IDs must be ≤ 255. For a spinner see `tools/generate_spinner_icons.py`.
2. **Build an icon library** in the DGUS IDE from those images and save it as `<slot>_NAME.icl`
   (we use `29_SPIN.icl`). *The slot number is the library number used in the record.* Check with
   `check_icl.py` that it overlaps nothing. (The stock `25_ICO.icl` can be used for a quick test: its
   toggle icons 35 → 36 animate.)
3. **Add the record** to the page: `make_icon_animation_record(x, y, start_icon, end_icon, icon_lib,
   frame_time, stop_icon, vp_addr, v_start=1, v_stop=0, opaque=True)`.
   * `frame_time` is in 20 ms cycles; `5` ≈ 10 frames per second.
   * `opaque=True` is the robust choice: draw the frames on the page's exact background colour
     (`BG_DARK = (18,18,18)`) and there is nothing to tune. Transparent mode keys out a colour and has a
     `Filter_Set` threshold you would have to tune by eye.
4. **Firmware:** `SendValueToTFT(1, vp)` when the page appears, `SendValueToTFT(0, vp)` when it leaves
   (`DgusTFT::WaitStatus()` does this for the wait screens).
5. Draw the page art so the **resting state looks right**: the animation's stop icon (and the picture
   under it) is what shows when the VP is 0.

What we built on this: `ui_features.WAIT_BADGES` (one badge per wait screen: position, glyph, colour,
icon IDs), `generate_spinner_icons.py` (frames), `patch_14showfile.py` (records when
`SPINNER_ANIMATION = True`). Keep `SPINNER_ANIMATION = False` until `29_SPIN.icl` is on the display:
pointing an animation at a missing library shows garbage.

*Alternatives that need no new file:* moving text (the wait screens write "Homing.. X-6 Y-20 Z4" with
changing dots every 400 ms — also proves the firmware is alive), and page-pair state indication
(Tools page 207 vs 209 differ only by the light button's colour; the firmware opens the page that
matches the state).

## 3.5 Make buttons show a pressed state **[SPEC]**

Native feature of the touch record's **`Pic_On`** field (2.2): while a button is held, the display copies
the button's rectangle out of *another page's picture* and shows it over the button.

1. For each page with buttons, render the page's art with every button in a "lit" style, then cut it down
   to the touch rectangles and fill the rest black (it is never shown; black keeps the JPEG small).
   `generate_screens.generate_pressed()` does exactly this (`btn()` has a `_PRESSED` mode: 30 % lighter
   fill + 2 px orange rim).
2. Give each pressed picture an ID that is not a page. `tools/press_effect.py` assigns **page + 34** for
   pages 1–34 (as the stock UI does) and 69–83 for the special pages; pages with identical art
   (ENG mirrors etc., the `TWIN` table) share one picture. IDs 35–83 are reserved for this.
3. `generate_dwin_controls.py` writes the ID into every zone's `Pic_On`.
4. The pictures must be **in the rebuilt picture library** — the IDE import list is the 143 BMPs in
   `ICL_SOURCE_BMPS/`. `cross_check_display.py` fails if a zone names a picture that does not exist or
   whose twin pages have different art.

Not given an effect: file-list rows (the firmware prefixes the tapped file with `> `). The stock
colour-change trick (`SendColorToTFT` to `TXT_DISCRIBE_n`) only works for records whose SP points at a
RAM parameter block, which ours do not.

## 3.6 Build the picture library (manual, in DWIN's IDE)

The display shows pictures **only** from `16_68_.icl`. `*.bmp` files are source material and are ignored
by the display (its flasher counts only CFG/Code/BIN/DZK/HZK/ICL/LIB/WAE/UIC/GTF/DAT files).

1. `python tools/build_release.py --allow-stale-icl --out release_vN` (or just
   `python tools/generate_screens.py`) to make the BMPs. The packager puts exactly the images that
   belong in the library into `ICL_SOURCE_BMPS/` (pages 0–217 minus hidden pages, plus pressed pictures
   35–83; **not** the boot-animation frames 218–256).
2. Run the DGUS IDE (`DGUS/DGUS_V7649/DGUS_V7.649.exe`, or `DWprj.hmi` for the project), use the **ICL
   tool**, import every image in `ICL_SOURCE_BMPS/` in numeric order (the picture index must equal the
   number in the file name), generate, and save as `DWIN_SET/16_68_.icl`.
3. `python tools/check_icl.py` → must print `ICL is current` and no `FLASH OVERLAP`. It decodes the
   library you just built and compares every picture with its BMP (lossy JPEG ⇒ it tolerates ringing but
   flags real differences).
   **Alternative (experimental, no IDE):** `python tools/build_icl.py` writes
   `DWIN_SET/auto_icl/16_68_.icl` from the same BMPs and verifies it with the independent decoder;
   `python tools/check_icl.py --icl DWIN_SET/auto_icl/16_68_.icl` re-checks it. Flash-test it before relying on it.
4. Do **not** use `TOOL\DW_ICON.exe` (wrong, headerless format) and do **not** let the IDE regenerate
   `13/14/22` files — ours come from the scripts.

## 3.7 Flash the display and the mainboard

1. **SD card: FAT32 with a 4096-byte allocation unit.** Right-click formatting in Windows does *not*
   give you this. In an administrator command prompt: `format X: /q /fs:fat32 /a:4096` (erases the card).
   With any other cluster size the display's blue screen reports **0 files** and flashes nothing —
   this cost us two test rounds. **[HW]**
2. Copy the `DWIN_SET` folder (just the display files, no BMPs) to the **card root**.
3. Printer **off** → card into the small USB port on the **back of the display** → power on. A blue
   screen lists what it flashed (`.CFG 1, .BIN 4, .DZK 1, .HZK 1, .ICL 2…`, all non-zero) and ends with
   `END !`. Power off, remove the card.
4. Mainboard: put `firmware.bin` on a card root, card into the **front** slot, power on; it flashes by itself.
5. **If a bad flash leaves the display blank, frozen or garbled: power it off completely, wait 15–20 seconds
   so the capacitors discharge, then reflash the last known-good set.** A plain re-flash while still
   powered does *not* recover it. `release/` is the last known-good set.

## 3.8 Turn on / off optional features

`tools/ui_features.py` is the switchboard (all default to what is safe on Marlin 2.0.8):

| Flag | Meaning |
|---|---|
| `HAS_INPUT_SHAPING`, `HAS_MPC`, `HAS_M1024` | Whether the firmware really has `M593`, `M306`, `M1024`. If `False` the screens that need them are hidden (no buttons, no zones). |
| `SPINNER_ANIMATION` | Spinner animation icons on wait screens (needs `29_SPIN.icl`). |
| `PROGRESS_BARS` | Process-bar controls on Printing and Leveling. |
| `PRESS_EFFECT` | Pressed-button pictures + `Pic_On` in the touch file. |
| `PRINT_SETTINGS_ROWS` | The layout (y positions, key codes) of the Print Settings screen. |
| `WAIT_BADGES` | Position/glyph/colour/icon IDs of the wait-screen badges. |
| `FLASH_RENAMES` | The shipped names of the icon library and font. |

Values the art quotes (preheat temperatures, grid size, Marlin version) are **read from
`Configuration.h`/`Version.h`** so the screens cannot disagree with the firmware.

# Part 4 — What works, what is unproven, what failed

## Hardware-confirmed **[HW]**
* Boot, serial link, touch, the redesigned UI from a DGUS-IDE-built `16_68_.icl`.
* Status-bar text, the 0-based page table (after the fix), text and integer records, the wait-screen
  status line, the step-size text, the Home X/Y/Z/All fix (`HomingComplete`), the new firmware's navigation.
* **Animation icons** (a test toggle animated on the homing screen).
* `ChangePageOfTFT_DevicePage()` for "back" navigation.

## Built, build-verified, **not yet tested on the printer**
Pressed-button effect, process bars, the spinner animation, the Print Settings −/+ rework, the file-list
selection marker, the Terminal font, the Z-offset preservation across leveling, the flash re-layout
(`25_`/`26_` names, bigger library).

## Experimental, decoder-verified only
`tools/build_icl.py` (script-built picture/icon library). Test set: `release_v2/EXPERIMENTAL_SCRIPT_ICL/`.

## Tried and **parked** (do not repeat without new information)
* **Boot animation.** Image Animation (`0x5A04`) was tried six ways over a day (hand-built records,
  IDE-generated, isolated page, cross-test with another project's real files — which *did* play, proving
  the mechanism works on this display — and a from-scratch IDE project that produced a blank,
  unresponsive display). A record with `ICL_LIB_ID = 1` corrupted text rendering display-wide. The
  display was recovered by a full power-down and reflash. Since then the guide told us: Image Animation
  returns to its page after playing, `Pic_Begin < Pic_End`, `ICL_LIB_ID 0` = the background library;
  *Animation Icon* is a different, VP-driven control. The boot frames live in `34_BootAnim.icl`
  (built from `generate_boot_animation.py` + DWIN's Movie2ICL) but are not shipped. The old 1-based table
  bug and the library/ICO flash-slot overlap may have contributed — neither was known at the time.
* **`22_Config.bin` regenerated from a fresh IDE project** — display would not boot. Always use the stock one.
* **Loose BMP files** — ignored by the display.

## Known gaps / ideas
* Page 214 (thumbnail) is an unreachable stub — Marlin 2.0.8 has no G-code thumbnail parsing.
* Input Shaping (`M593`) and MPC (`M306`) exist only on the `upgrade-2.1.x` branch, which never booted
  (it links at 0xC000 instead of 0x8000 and lacks ~20 HAL fixes).
* `M1024` (stock auto-Z-offset command) is not implemented anywhere; its screen is hidden.
* Text boxes are top-aligned; the status-bar text may sit slightly high next to its icons — unverified.
* A real **spinner** needs `29_SPIN.icl` built in the IDE.
* A script-written library is verified by our decoder but not yet by the display (see above).

# Part 5 — The tools (`tools/`)

Run everything **from the repository root**: `python tools/<name>.py`. Needs Python 3 with **Pillow**.
(When running with `python -I`, the tools add their own folder to the path.)

## 5.1 How they fit together

```
 ui_features.py ──┬─> generate_screens.py ──> DWIN_SET/NNN.bmp   (pages + pressed pictures)
 press_effect.py ─┤        │                         │  (manual: DGUS IDE)
                  │        │                         v
                  │        │                  DWIN_SET/16_68_.icl
                  ├─> generate_dwin_controls.py ──> DWIN_SET/13TouchFile.bin
                  ├─> patch_14showfile.py  ───────> DWIN_SET/14ShowFile.bin   (from 14ShowFile.base.bin)
                  └─> generate_spinner_icons.py ──> DWIN_SET/spinner_icons/*.bmp  (-> 29_SPIN.icl, manual)

 cross_check_display.py  = art  vs  touch  vs  show file  vs  C++ handlers  vs  VP addresses
 check_icl.py            = the compiled library on the display's side  vs  the BMPs; flash-slot overlaps
 build_release.py        = runs all of the above, builds the firmware, assembles a flashable folder
```

# Part 6 — Pitfalls (each of these cost real time)

1. **SD card must be FAT32 / 4096-byte allocation unit** or the display flashes nothing (blue screen shows 000).
2. **The show-file page table is 0-based.** `16 + 4*pageID`.
3. **The display only shows the `.icl`.** Changing a BMP, a touch zone and a record without rebuilding the
   library gives new zones over old art. Always `check_icl.py`.
4. **Flash slot overlaps** silently corrupt other files (library vs icon library vs font). Mind `FLASH_RENAMES`.
5. **Never `ChangePageOfTFT()` with a stored page** — use `ChangePageOfTFT_DevicePage()`.
6. **Never change page during the boot animation.**
7. **Animation icons need the VP written** — they do not free-run.
8. **Text records are top-left aligned and clip at `Text_Length`** (30 bytes today; the window per text VP is 0x30 words).
9. **A button with no handler, or a handler with no button, is a bug the display will never report.** Run `cross_check_display.py`.
10. **A button that does nothing in some state shouldn't be drawn** (we removed BACK from the Printing screens).
11. **Stale-VP read-back**: the old SAVE button read four VPs the page never let you edit, re-applying the values
    from when the page opened and undoing G-code changes. Apply changes immediately instead.
12. **Hardware validation of "big batch" changes can fail for build reasons** — if a flash regresses, rebuild and
    reflash the *same* source before bisecting.
13. **A failed/blank display flash**: power off 15–20 s, then reflash a known-good set.
14. **Tooling gotcha (this environment):** inline Python heredocs mangle backslashes (`\n`, `\xff`) — write
    scripts to files or use `chr(92)`.
